# 真实智能体业务场景：物流异常分诊

这个场景让成熟智能体客户端实际完成一项业务任务，而不是按固定顺序手写 MCP 调用。智能体需要自行读取规则、选择工具、计算时长、处理失败、创建内部草稿并给出带工单编号的结果。

**模型推理、客户端、HTTP MCP、网关、PostgreSQL、Redis 和工具执行均真实运行；商户及物流数据由本地测试业务服务提供。** 不连接真实客户系统，不发送邮件、不退款。

## 参与者和任务

- Codex CLI：`codex-east`、`codex-west` 两个独立智能体会话。
- Claude Code：`claude-east`、`claude-west` 两个独立智能体会话。
- 每个会话仅连接自己的组端点，暴露 4 个 MCP 工具：`find_orders`、`shipping_policy`、`track_order`、`draft_escalation`。
- 两家商户各有 5 个相同编号但状态不同的订单，各自使用不同的上游密钥及升级阈值。
- 所有业务事实由工具返回；[任务提示词](agents/task.md) 不包含订单数据或预期答案，也不预先指定工具调用顺序。

| 商户 | 阈值 | 应升级订单 | 不应升级订单 |
|---|---|---|---|
| east | 严格超过 48 小时 | ORD-101：72h；ORD-104：96h | ORD-102 已送达；ORD-103 24h；ORD-105 已取消 |
| west | 严格超过 72 小时 | ORD-102：96h；ORD-104：84h | ORD-101 60h；ORD-103 48h；ORD-105 已取消 |

业务时钟固定为 `2026-09-27T12:00:00+00:00`，计算不依赖机器当前时间。每个东区智能体第一次查询 ORD-101 时独立遇到一次 HTTP 503，必须重试才能正确完成任务。

## 执行

要求：Docker Compose、已安装的项目依赖，以及已登录且可实际调用模型的客户端。脚本不读取或复制 CLI 的模型凭据文件，不修改全局客户端配置。

```sh
uv sync --frozen
codex login status
claude auth status
uv run python scenarios/fulfillment/run.py
```

也可以仅运行一个客户端：

```sh
uv run python scenarios/fulfillment/run.py --clients codex
uv run python scenarios/fulfillment/run.py --clients claude
```

每次执行会调用真实模型，使用已配置的客户端接入和可用额度。Codex 使用 `--ignore-user-config` 下的 CLI 默认模型，保留已有登录；Claude Code 使用现有用户模型接入，关闭 hooks 和内置工具，仅启用本次 MCP。脚本不显式指定模型，不能保证未来运行使用与本次相同的模型。客户端名称不代表模型名称；实际报告分开记录。

脚本自动完成：

1. 创建随机端口、独立 Compose 项目、临时 PostgreSQL 和 Redis。
2. 启动测试业务 HTTP 服务，生成两个上游密钥，启动两个网关 worker。
3. 迁移、插件检查、目录同步、初始化临时管理员。
4. 经管理 API 创建 Secret → ConfigProfile → 静态认证 → 四个组 → 工具绑定 → 启用。
5. 预检每组只暴露 4 个工具，schema 不包含 runtime/api_key，跨组 Key 返回 401。
6. 并发运行最多 4 个真实智能体会话；每个会话有独立工作目录和组凭据。
7. 以业务服务实际保存的工单及调用轨迹核对答案；随后撤销所有组 Key，并检查 401。
8. 保存脱敏结果，终止服务，删除本次临时容器和数据。

通过返回退出码 0；任何模型失败、业务结果不正确、认证断言失败或清理失败均返回非零。默认单个智能体超时为 240 秒，可以通过 `--timeout` 设置；网络超时或账号限额属于运行环境失败，不能伪装成成功。

## 可验证性

判定器不只检查最终文本，还检查：

- 恰好升级正确的两张订单，并对其余三张订单给出跳过结果。
- 规则阈值、商户、业务时间和停滞小时数正确。
- 工单号确实存在于业务状态，状态为 draft，且本智能体实际发出了相应写请求。
- 本组全部上游调用都使用正确商户身份。
- 没有不符合规则的草稿创建尝试，也没有通过其他工具绕过 MCP。
- 东区的 503 后存在成功重试。
- 输出未包含本次测试生成的凭据。

测试插件还声明了一个 `refund` 哨兵工具，但不对任何组绑定；预检保证它不会进入智能体工具列表。两个客户端处理同一商户时会重复提出同一草稿创建请求，测试业务系统以商户/订单为键保证幂等，最终只能有 4 个工单。这是上游实现的幂等性，不是网关提供的自动去重。

[判定器单元测试](test_evaluation.py) 检查“回答看起来正确但没有实际调用或工单”、跨商户污染、伪造工单号、违规写入及未恢复故障等情况都不能被判成功：

```sh
uv run python -m pytest scenarios/fulfillment/test_evaluation.py -q
```

## 产物

默认写入 `artifacts/fulfillment/<UTC时间>/`，可以用 `--output 新目录` 指定：

- `summary.json`：客户端版本、每个任务耗时、客户端报告的模型、模型 usage、MCP 调用、最终答案及逐项判定。
- `business-evidence.json`：业务系统实际保存的草稿、按组及调用 ID 关联的上游事件。
- `services.log`：基础设施和网关脱敏日志。

不会保存完整模型内部推理流。测试用真实随机 Key 会在写入产物前替换为 `[REDACTED]`。JSON 中的业务订单、理由和工单号均为合成测试数据。

首次实测报告及捕获证据：[2026-09-27 测试报告](../../docs/reports/fulfillment-2026-09-27/report.md)。
